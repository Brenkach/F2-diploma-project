**Аналітичний висновок до підрозділу 1.2**

Порівняльний аналіз аналогів засвідчує, що їхні ключові недоліки зумовлені не монолітною чи мікросервісною структурою як такою, а способом організації даних, подій та обчислень. Спільною для всіх трьох систем є проблема подвійного запису (dual write), проте ступінь її підтвердженості для кожної системи різний. Подвійний запис полягає в тому, що зміна стану в основній СУБД і публікація відповідної події або оновлення вторинного сховища виконуються як дві незалежні операції без спільної транзакції. Для TaskRabbit застосування патерну Transactional Outbox у відкритих джерелах не підтверджено, а взаємодію між MySQL і Kafka (раніше між MySQL і шиною resque-bus на Redis) організовано саме за принципом подвійного запису [x]. Для Kabanchik.ua механізм синхронізації PostgreSQL та Elasticsearch не задокументовано, тому ризик розбіжності пошукового індексу з джерелом істини є інженерним припущенням, а не встановленим фактом. Thumbtack, згідно з власними технічними публікаціями, реалізував наскрізні гарантії доставки подій власними засобами та визнав це складною задачею [x].

Другим системним чинником є розподіл даних між кількома сховищами з узгодженістю в кінцевому підсумку (eventual consistency). Поліглотне зберігання TaskRabbit (MySQL, PostgreSQL, Snowflake) та Thumbtack (PostgreSQL, DynamoDB, Elasticsearch, BigQuery) унеможливлює ACID-транзакції між доменами та переносить забезпечення цілісності даних на рівень прикладної логіки. Третім чинником є виконання обчислювально важких операцій у синхронному циклі HTTP-запиту. У Kabanchik.ua до таких операцій належать ранжування виконавців за геолокацією та аналіз фотографій [x], унаслідок чого час відповіді та пропускна здатність WSGI worker-процесів залежать від тривалості обчислень. Вартість супроводу цієї системи додатково підвищують співіснування двох моделей виконання (WSGI та asyncio) і застарілий технологічний стек: CoffeeScript та Python 3.6, підтримку якого припинено у грудні 2021 р.

Для Thumbtack визначальними чинниками є:
- залежність від керованих хмарних сервісів: задокументовано випадки, коли зміни API BigQuery порушували роботу конвеєрів у production-середовищі [x];
- необхідність масових повторних спроб через помилки 500/503;
- мультихмарні витрати на трафік;
- обмеження масштабування операцій запису одним master-вузлом;
- операційна складність підтримки трьох мов програмування.

Досвід TaskRabbit, декомпозиція моноліту якого триває понад десять років, дає підстави вважати, що перехід до мікросервісів без сформованих меж доменів і механізмів надійної доставки подій не усуває технічний борг, а розподіляє його між компонентами. Інцидент квітня 2018 р., унаслідок якого вебсайт і мобільний застосунок TaskRabbit були недоступні близько двох діб [x], є задокументованим фактом. Висновок про недостатню ізоляцію відмов як чинник масштабу цього простою є інтерпретацією автора.

Архітектуру проєкту «Сусід» спрямовано на усунення виявлених причин зі збереженням монолітної структури. Модульний моноліт на Python / Flask з явними межами доменних модулів забезпечує єдину модель виконання та єдиний процес розгортання. Водночас зберігається можливість виокремлення окремих модулів у сервіси за обґрунтованої потреби, що дає змогу уникнути передчасної декомпозиції.

Використання PostgreSQL як єдиного джерела істини дає змогу виконувати зміни доменного стану в межах однієї ACID-транзакції. Похідні дані (рейтинги, результати аналізу зображень, векторні представлення) при цьому розглядаються як відновлювані з основної бази даних. Проблему подвійного запису усунено застосуванням патерну Transactional Outbox: подія фіксується в таблиці outbox у тій самій транзакції, що й бізнес-зміна, а окремий ретранслятор (relay) публікує її до брокера. Це забезпечує семантику доставки «щонайменше один раз» (at-least-once) за умови ідемпотентності обробників.

Перерахунок рейтингу та аналіз фотографій винесено в асинхронні Celery workers, тому час відповіді REST API не залежить від тривалості обчислень. Розподіл задач за окремими чергами обмежує вплив перевантаження або збою ML-задач на обслуговування запитів. Локальне виконання відкритих моделей (networkx, scikit-learn, sentence-transformers, моделі обробки зображень) усуває залежність від API керованих хмарних сервісів і пов'язані з ними змінні витрати. Telegram-бот реалізовано як окремий клієнт REST API, що запобігає дублюванню бізнес-логіки та ізолює відмови: збій бота не впливає на роботу ядра системи.

Запропоноване рішення має три прийняті проєктні обмеження.

1. Масштабування є переважно вертикальним у межах одного вузла, а PostgreSQL становить єдину точку відмови. Для цільового масштабу проєкту (пілотне розгортання в межах обмеженої територіальної спільноти) навантаження, за інженерною оцінкою автора, не перевищує можливостей одного сервера. Відновлюваність забезпечується резервним копіюванням та архівуванням журналу WAL.
2. Redis як брокер повідомлень не гарантує довговічності, тому під час збою можлива втрата повідомлень. Цей ризик компенсується тим, що первинним носієм подій є таблиця outbox у PostgreSQL. Компенсація є повною лише за умови, що подія вважається обробленою після підтвердження з боку споживача або періодичної звірки, а не одразу після передачі до брокера. За такої умови втрата повідомлення в брокері спричиняє затримку обробки, а не втрату даних.
3. Локальні ML-моделі конкурують з іншими компонентами за обчислювальні ресурси вузла, що зумовлює необхідність контролю паралелізму worker-процесів.

Отже, на етапі проєктування (Розділ 2) передбачено реалізацію таких архітектурних вимог:
- АВ-1: декомпозиція системи на доменні модулі з явними інтерфейсами та забороною прямого доступу до таблиць інших модулів;
- АВ-2: PostgreSQL як єдине джерело істини з відновлюваністю всіх похідних даних;
- АВ-3: Transactional Outbox з ретранслятором, підтвердженням обробки та ідемпотентними споживачами;
- АВ-4: винесення всіх обчислювально важких операцій з циклу HTTP-запиту в окремі черги Celery з обмеженням паралелізму та політикою повторних спроб;
- АВ-5: виконання ML-компонентів виключно на локальних відкритих моделях без залежності від зовнішніх API;
- АВ-6: взаємодія Telegram-бота з ядром системи виключно через версіонований REST API;
- АВ-7: стратегія резервного копіювання та відновлення PostgreSQL, а також кількісна оцінка допустимого навантаження на один вузол.

Наведені вимоги визначають структуру Розділу 2: від доменної моделі та схеми даних до проєктування механізму доставки подій і конвеєра асинхронної обробки.
