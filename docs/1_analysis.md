**Аналітичний висновок до підрозділу 1.3**

Порівняльний аналіз аналогів засвідчує, що їхні ключові недоліки зумовлені не монолітною чи мікросервісною структурою як такою, а способом організації даних, подій та обчислень. Спільною для всіх трьох систем є проблема подвійного запису (dual write), проте ступінь її підтвердженості для кожної системи різний. Подвійний запис полягає в тому, що зміна стану в основній СУБД і публікація відповідної події або оновлення вторинного сховища виконуються як дві незалежні операції без спільної транзакції. Для TaskRabbit застосування патерну Transactional Outbox у відкритих джерелах не підтверджено, а взаємодію між MySQL і Kafka (раніше між MySQL і шиною resque-bus на Redis) організовано саме за принципом подвійного запису [10]. Для Kabanchik.ua механізм синхронізації PostgreSQL та Elasticsearch не задокументовано, тому ризик розбіжності пошукового індексу з джерелом істини є інженерним припущенням, а не встановленим фактом. Thumbtack, згідно з власними технічними публікаціями, реалізував наскрізні гарантії доставки подій власними засобами та визнав це складною задачею [9].

Другим системним чинником є розподіл даних між кількома сховищами з узгодженістю в кінцевому підсумку (eventual consistency). Поліглотне зберігання TaskRabbit (MySQL, PostgreSQL, Snowflake) та Thumbtack (PostgreSQL, DynamoDB, Elasticsearch, BigQuery) унеможливлює ACID-транзакції між доменами та переносить забезпечення цілісності даних на рівень прикладної логіки. Третім чинником є виконання обчислювально важких операцій у синхронному циклі HTTP-запиту. У Kabanchik.ua до таких операцій належать ранжування виконавців за геолокацією та аналіз фотографій [8], унаслідок чого час відповіді та пропускна здатність WSGI worker-процесів залежать від тривалості обчислень. Вартість супроводу цієї системи додатково підвищують співіснування двох моделей виконання (WSGI та asyncio) і застарілий технологічний стек: CoffeeScript та Python 3.6, підтримку якого припинено у грудні 2021 р.

Для Thumbtack визначальними чинниками є:
- залежність від керованих хмарних сервісів: задокументовано випадки, коли зміни API BigQuery порушували роботу конвеєрів у production-середовищі [9];
- необхідність масових повторних спроб через помилки 500/503;
- мультихмарні витрати на трафік;
- обмеження масштабування операцій запису одним master-вузлом;
- операційна складність підтримки трьох мов програмування.

Досвід TaskRabbit, декомпозиція моноліту якого триває понад десять років, дає підстави вважати, що перехід до мікросервісів без сформованих меж доменів і механізмів надійної доставки подій не усуває технічний борг, а розподіляє його між компонентами. Інцидент квітня 2018 р., унаслідок якого вебсайт і мобільний застосунок TaskRabbit були недоступні близько двох діб [11], є задокументованим фактом. Висновок про недостатню ізоляцію відмов як чинник масштабу цього простою є інтерпретацією автора.

Архітектуру проєкту «Сусід» спрямовано на усунення виявлених причин зі збереженням монолітної структури. Модульний моноліт на Python / Flask з явними межами доменних модулів забезпечує єдину модель виконання та єдиний процес розгортання. Водночас зберігається можливість виокремлення окремих модулів у сервіси за обґрунтованої потреби, що дає змогу уникнути передчасної декомпозиції.

Використання PostgreSQL як єдиного джерела істини дає змогу виконувати зміни доменного стану в межах однієї ACID-транзакції. Похідні дані (рейтинги, результати аналізу зображень, векторні представлення) при цьому розглядаються як відновлювані з основної бази даних. Проблему подвійного запису усунено застосуванням патерну Transactional Outbox: подія фіксується в таблиці outbox у тій самій транзакції, що й бізнес-зміна, а окремий ретранслятор (relay) публікує її до брокера. Це забезпечує семантику доставки «щонайменше один раз» (at-least-once) за умови ідемпотентності обробників.

Перерахунок рейтингу та аналіз фотографій винесено в асинхронні Celery workers, тому час відповіді REST API не залежить від тривалості обчислень. Розподіл задач за окремими чергами обмежує вплив перевантаження або збою ML-задач на обслуговування запитів. Локальне виконання відкритих моделей (networkx, scikit-learn, sentence-transformers, моделі обробки зображень) усуває залежність від API керованих хмарних сервісів і пов'язані з ними змінні витрати. Telegram-бот реалізовано як окремий клієнт REST API, що запобігає дублюванню бізнес-логіки та ізолює відмови: збій бота не впливає на роботу ядра системи.

Запропоноване рішення має три прийняті проєктні обмеження.

1. Масштабування є переважно вертикальним у межах одного вузла, а PostgreSQL становить єдину точку відмови. Для цільового масштабу проєкту (пілотне розгортання в межах обмеженої територіальної спільноти) навантаження, за інженерною оцінкою автора, не перевищує можливостей одного сервера. Відновлюваність забезпечується резервним копіюванням та архівуванням журналу WAL.
2. Redis як брокер повідомлень не гарантує довговічності, тому під час збою можлива втрата повідомлень. Цей ризик компенсується тим, що первинним носієм подій є таблиця outbox у PostgreSQL. Компенсація є повною лише за умови, що подія вважається обробленою після підтвердження з боку споживача або періодичної звірки, а не одразу після передачі до брокера. За такої умови втрата повідомлення в брокері спричиняє затримку обробки, а не втрату даних.
3. Локальні ML-моделі конкурують з іншими компонентами за обчислювальні ресурси вузла, що зумовлює необхідність контролю паралелізму worker-процесів.

Отже, на етапі проєктування (Розділ 2) передбачено реалізацію таких архітектурних вимог:
- АВ-1: декомпозиція системи на доменні модулі з явними інтерфейсами та забороною прямого доступу до таблиць інших модулів;
- АВ-2: PostgreSQL як єдине джерело істини з відновлюваністю всіх похідних даних;
- АВ-3: Transactional Outbox з ретранслятором, підтвердженням обробки та ідемпотентними споживачами;
- АВ-4: винесення всіх обчислювально важких операцій з циклу HTTP-запиту в окремі черги Celery з обмеженням паралелізму та політикою повторних спроб;
- АВ-5: виконання ML-компонентів виключно на локальних відкритих моделях без залежності від зовнішніх API;
- АВ-6: взаємодія Telegram-бота з ядром системи виключно через версіонований REST API;
- АВ-7: стратегія резервного копіювання та відновлення PostgreSQL, а також кількісна оцінка допустимого навантаження на один вузол.

Наведені вимоги визначають структуру Розділу 2: від доменної моделі та схеми даних до проєктування механізму доставки подій і конвеєра асинхронної обробки.
## Концептуальна модель To-Be

У цільовому стані взаємодія замовника, майстра та системи відбувається за таким сценарієм.

1. **Пошук.** Замовник знаходить майстрів у каталозі за категорією, районом і текстовим запитом. Індексація виконується засобами PostgreSQL (pg_trgm), сортування — за рейтингом довіри. Усуваються вузькі місця Б1.1-Б1.3.
2. **Створення запиту.** Замовник описує проблему й додає фотографії. Метадані EXIF видаляються перед збереженням. Асинхронний worker-процес визначає тип несправності та формує підказку: перелік матеріалів та інструментів. Підказка відображається майстру в картці замовлення, і майстер її підтверджує або коригує (усунення Б2.3).
3. **Життєвий цикл замовлення.** Замовлення проходить стани «створено → прийнято → виконується → виконано → підтверджено / оскаржено». Допустимі переходи визначені скінченним автоматом і контролюються на рівні застосунку та обмежень цілісності PostgreSQL (усунення Б1.4, Б2.1).
4. **Доставка подій.** Кожна зміна статусу записується в таблицю outbox у тій самій транзакції. Ретранслятор публікує події до черги Celery із семантикою «щонайменше один раз», а споживачі є ідемпотентними. Сповіщення в Telegram, перерахунок рейтингу та аналіз фотографій виконуються асинхронно (усунення Б2.4).
5. **Відгук.** Відгук приймається лише для замовлення в статусі «підтверджено» й лише один на замовлення; обмеження реалізується складеним зовнішнім ключем і унікальним індексом у PostgreSQL (усунення Б2.2, Б3.2).
6. **Рейтинг довіри.** Рейтинг обчислюється із зваженим байєсівським згладжуванням:

$$R = \frac{\sum_{k=1}^{v} w_k r_k + m \cdot C}{\sum_{k=1}^{v} w_k + m} + B - P,$$

де $r_k$ — оцінка $k$-го відгуку; $w_k = w^{d}_k \cdot 2^{-\Delta t_k/\tau}$ — вага відгуку; $w^{d}_k = \alpha$ ($\alpha > 1$), якщо автор відгуку й майстер належать до одного району, і $w^{d}_k = 1$ в іншому випадку; $\Delta t_k$ — вік відгуку; $\tau$ — період напіврозпаду; $m$ — параметр згладжування; $C$ — середня оцінка за платформою; $B$ — бонус за верифікацію; $P$ — штраф за виявлені патерни накрутки. Значення параметрів $\alpha$, $\tau$, $m$ визначаються експериментально в Розділі 3. Користувач отримує «паспорт рейтингу»: розкладку складових $R$ (усунення Б3.1, Б3.4, Б3.5).
7. **Виявлення накруток.** Асинхронний worker-процес будує граф взаємодій «замовник — майстер» (networkx), обчислює ознаки (частота відгуків за інтервал часу, взаємність оцінок, коефіцієнт кластеризації, схожість текстів за векторними представленнями) і передає їх класифікатору (scikit-learn). Підозрілі відгуки потрапляють у чергу модератора, а штраф $P$ застосовується до рейтингу (усунення Б3.3).

## Функціональні вимоги (Core Features)

Модуль «Доступ і верифікація»

- **Core Feature 1.** Реалізувати автентифікацію (електронна пошта та пароль, вхід через Telegram), рольову модель доступу (RBAC) для ролей «замовник», «майстер», «модератор», видачу підписаних JWT, верифікацію телефону та перевірку документів майстра модератором.

Модуль «Каталог»

- **Core Feature 2.** Забезпечити ведення профілів майстрів (послуги, ціни, портфоліо, райони обслуговування) та пошук у каталозі за категорією, районом і текстовим запитом із сортуванням за рейтингом довіри.

Модуль «Замовлення»

- **Core Feature 3.** Керувати життєвим циклом замовлення за скінченним автоматом («створено → прийнято → виконується → виконано → підтверджено / оскаржено») з валідацією переходів, збереженням історії статусів і обмеженнями цілісності на рівні PostgreSQL.

Модуль «Відгуки»

- **Core Feature 4.** Приймати відгук і оцінку лише для замовлень у статусі «підтверджено» за обмеженням «один відгук на замовлення» та надавати механізм подання скарг на відгук.

Модуль «Рейтинг довіри»

- **Core Feature 5.** Обчислювати рейтинг довіри (байєсівське згладжування, вага за районом автора, затухання за давністю, бонус за верифікацію) та формувати «паспорт рейтингу» з розкладкою складових.

Модуль «Антинакрутка і модерація»

- **Core Feature 6.** Виявляти підозрілі патерни оцінювання за графом взаємодій і ML-класифікатором, застосовувати штрафи до рейтингу та формувати чергу скарг і підозрілих відгуків для модератора з панеллю статистики.

Модуль «Події та сповіщення»

- **Core Feature 7.** Гарантувати доставку подій за патерном Transactional Outbox, виконувати асинхронні задачі в Celery (перерахунок рейтингу, аналіз зображень, сповіщення) і надсилати користувачам повідомлення про зміну статусу замовлення через Telegram-бота.

Модуль «Діагностика за фото»

- **Core Feature 8.** Визначати за фотографією несправності її тип (zero-shot класифікація) і формувати для майстра підказку з переліком матеріалів та інструментів за базою знань, зберігаючи правки майстра для оцінювання якості.

## Постановка задачі

Таким чином, метою кваліфікаційної роботи є проєктування та розробка веб-платформи на основі модульного моноліту з асинхронним шаром обробки подій (Flask, PostgreSQL, Celery, Redis) для вирішення задачі підвищення достовірності вибору виконавця локальних послуг шляхом обчислення районного рейтингу довіри, стійкого до накрутки відгуків, із гарантованою доставкою подій за патерном Transactional Outbox, виявленням накруток за графом взаємодій і класифікатором та попередньою діагностикою запиту за фотографією.
