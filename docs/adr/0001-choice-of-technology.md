## Context

Зміна стану замовлення, відгуку чи рейтингу повинна спричиняти асинхронні побічні ефекти: перерахунок рейтингу, аналіз фотографій, сповіщення в Telegram. Узгодження запису в СУБД і публікації події в брокер без спільної транзакції створює проблему подвійного запису (dual write): за збою між двома операціями подія втрачається або публікується без зміни стану (Розділ 1, підрозділ 1.3).

Обмеження, що випливають із SRS:

- одиночний вузол 4 vCPU, 8 ГБ RAM, спільний із PostgreSQL та ML-моделями (CON-01);
- безкоштовне програмне забезпечення, без керованих хмарних сервісів (CON-02);
- нуль втрачених подій при перезапуску Redis і worker-процесів ([SRS-NFR-ASYNC-05](../srs.md#srs-nfr-async-05));
- Outbox lag p95 ≤ 5 с ([SRS-NFR-ASYNC-01](../srs.md#srs-nfr-async-01));
- очікуване навантаження запису ≤ 20 RPS ([SRS-NFR-PERF-03](../srs.md#srs-nfr-perf-03)), тобто порядку десятків подій за секунду.

## Alternatives

| Альтернатива | Опис | Інженерні обмеження для проєкту |
|---|---|---|
| A. Transactional Outbox у PostgreSQL + Celery з брокером Redis | Подія записується в таблицю `outbox` у транзакції зі зміною стану; ретранслятор публікує її в Redis | Redis не гарантує довговічності черги; потрібна звірка опублікованих, але не оброблених подій |
| B. Transactional Outbox + Celery з брокером RabbitMQ | Те саме, але брокер RabbitMQ з довговічними чергами (quorum queues) | Додаткова платформа Erlang, вище споживання пам'яті на спільному вузлі; керування кластером і політиками черг; для навантаження в десятки подій за секунду гарантії довговічності надлишкові |
| C. Apache Kafka (Outbox + Debezium або власний продюсер) | Журнал подій із повторним читанням | Celery не має стабільної підтримки Kafka як брокера, тому потрібна заміна фонових задач на власних консюмерів; JVM і ZooKeeper/KRaft на спільному вузлі; складність набагато перевищує потребу |
| D. Черга в PostgreSQL (`SELECT … FOR UPDATE SKIP LOCKED`) без окремого брокера | Задачі читаються безпосередньо з таблиці | Немає інтеграції з Celery; опитування таблиці навантажує СУБД, що обслуговує також запити каталогу; відсутні готові механізми повторних спроб і розкладу |

## Decision

Обрано варіант A: Transactional Outbox у PostgreSQL, ретранслятор (Outbox Relay), Celery з брокером Redis.

Обґрунтування технічними метриками:

1. **Атомарність.** Запис події в `outbox` виконується в тій самій ACID-транзакції, що й зміна стану, тому подія не може бути втрачена окремо від зміни.
2. **Узгодженість із навантаженням.** Redis обробляє понад 10^4 простих операцій за секунду на одному ядрі, що на два порядки перевищує розрахункову потужність потоку подій; брокер із журналом (Kafka) не дає виграшу за цієї потужності.
3. **Ресурси спільного вузла.** Redis одночасно слугує брокером Celery, cache каталогу та лічильником rate limiting ([SRS-NFR-PERF-01](../srs.md#srs-nfr-perf-01), [SRS-NFR-SEC-05](../srs.md#srs-nfr-sec-05)), тому окремий брокер не потрібен.
4. **Готова інтеграція.** Celery має стабільну підтримку Redis як брокера, повторні спроби та розклад завдань (beat).
5. **Нуль втрат.** Довговічність забезпечує таблиця `outbox`, а не Redis. Рядок має поля `published_at` і `processed_at`. Ретранслятор повторно публікує події, у яких `published_at` старший за T = 5 хв, а `processed_at` порожнє. Споживачі ідемпотентні за `event_id` ([SRS-FUN-35](../srs.md#srs-fun-35)). Це гарантує семантику «щонайменше один раз».
6. **Затримка.** Ретранслятор читає пакети по 100 рядків з інтервалом 1 с через `FOR UPDATE SKIP LOCKED`, що дозволяє вкластися в Outbox lag p95 ≤ 5 с.

## Consequences

**Позитивні:**

- Атомарність зміни стану та події без розподілених транзакцій.
- Один додатковий компонент інфраструктури (Redis) замість двох.
- Нульова вартість ліцензій і хмарних сервісів.
- Можливість заміни брокера без зміни прикладного коду: ретранслятор ізольований від споживачів.

**Негативні та ризики:**

- **Недовговічність Redis.** За збою Redis з режимом AOF `appendfsync everysec` можлива втрата до ~1 с записів черги. Компенсація: звірка за `processed_at`; ціна — затримка обробки до T = 5 хв (учитується в [SRS-NFR-REL-04](../srs.md#srs-nfr-rel-04)).
- **Доставка «щонайменше один раз».** Кожен споживач повинен бути ідемпотентним, що збільшує обсяг коду й тестів (таблиця `processed_events`, унікальний ключ `event_id`).
- **Ріст таблиці `outbox`.** Потрібна періодична задача очищення оброблених записів (для утримання індексів і швидкості опитування).
- **Затримка опитування.** Інтервал 1 с додає до затримки до 1 с порівняно з push-моделлю (LISTEN/NOTIFY, CDC).
- **Поведінка Celery з Redis.** Повторна видача задач після visibility timeout за тривалих завдань (аналіз фото) може дублювати виконання; потрібні `acks_late` і значення timeout більше за максимальний час задачі.
- **Ліцензія Redis.** Починаючи з версії 7.4 ліцензія Redis змінилася з BSD на RSALv2/SSPLv1 (Redis 8 додав варіант AGPLv3). Пом'якшення: використання Redis 7.2 (остання версія під BSD) або протокольно сумісного форку Valkey; ризик Vendor Lock-in низький, бо брокер замінюється через конфігурацію Celery.
- **Відсутність повторного читання.** На відміну від Kafka, повторна обробка історичних подій можлива лише з таблиці `outbox` у межах строку зберігання.
- **Єдина точка відмови.** Redis і PostgreSQL працюють на одному вузлі; відновлення забезпечується [SRS-NFR-REL-01](../srs.md#srs-nfr-rel-01).

**Критерії перегляду рішення:** перехід на RabbitMQ або Kafka розглядається, якщо стійке навантаження перевищить 10^3 подій за секунду, з'явиться потреба повторного читання потоку подій кількома незалежними споживачами або система буде розгорнута більш ніж на одному вузлі.
